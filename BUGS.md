## BUG-001 — Некорректные даты импортировались в хранилище ✅ (Фаза 5, 2026-08-29)

- **Статус:** исправлен, регресс-тест на месте.
- **Область:** `src/lib/store/store.ts` → `importDocumentToStore` / `normalizeDate`.
- **Симптом:** операции с пустой, мусорной или календарно-несуществующей датой (`''`, `2026-13-45`, `2026-02-30`, `гарабаз`) записывались в store «как есть». `normalizeDate` прокидывал неразбираемое значение неизменным; `ymOf` строил из них битые месячные ключи (`2026-13`, `2026-26-02` и т.п.) — такие операции выпадали из всех месячных срезов и искажали «По месяцам».
- **Воспроизведение (до фикса):**
  ```
  npx tsx -e "import('./src/lib/store/store').then(m=>console.log(JSON.stringify(m.normalizeDate('2026-13-45'))))"
  → "2026-13-45" (должно было отклоняться)
  ```
- **Причина:** валидация даты отсутствовала — проверка была только на сумму.
- **Фикс:** новая экспортная `isValidISODate()` (формат + реальное число дней месяца, високосные корректны) и `if (!isValidISODate(date)) { skipped++; continue; }` в цикле импорта. Некорректные даты теперь попадают в `ImportResult.skipped` и не пишутся в хранилище. Поведение валидных форматов (ISO, `dd.mm.yyyy`) не изменилось.
- **Регресс:** test-edge-cases.ts блок [2] (6 проверок isValidISODate + 4 битые даты → `skipped`, 2 валидные → `added`), в том числе високосные 29.02.2024 ✓ / 29.02.2026 ✗. Полная регрессия 9 сьютов — 262/262.
- **Миграция данных:** не требуется — валидных записей не трогает; в хранилищах пользователей до этого фикса могли находиться битые даты (раритет: для этого нужен файл выписки с такими датами). При необходимости такие строки видны в журнале «Учёт» и не попадают в месячные итоги.
